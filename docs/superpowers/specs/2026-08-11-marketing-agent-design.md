# marketing-agent 설계

## 배경

영업/마케팅 현황을 정리하는 웹 애플리케이션. 다음 세 가지를 자동 생성한다:

- **현황진단**: 채널·캠페인별 성과와 강약점
- **진단/타임라인**: 진단이 회차(주/월/캠페인 단위)를 넘어 어떻게 이어지는지
- **Action Items**: 담당·기한·우선순위가 붙은 실행 항목

`~/gitspace/weekly-report-harness`(S.LSI 사업부 주간보고 multi-agent 하네스)의
아키텍처·정확도 규율을 영업/마케팅 도메인에 이식한다. 그 프로젝트가 세 번의
실측 교정을 거쳐 확립한 규율(독립 재도출, 축자 인용 그라운딩, 판단 보류 표기,
반박 검증)을 처음부터 갖고 시작하는 것이 이 설계의 핵심 가치다 — 같은 함정을
다시 겪지 않기 위해서다.

## 목표 / 비목표

**목표**
- 사용자가 입력한 영업/마케팅 자료로부터 현황진단·타임라인·Action Items를 생성
- 하네스의 정확도 규율(그라운딩·독립 재도출·판단 보류 표기)을 1차부터 적용
- 웹 대시보드에서 결과를 조회

**비목표 (1차 범위 제외)**
- CRM/GA4 등 외부 데이터 소스 연동 — 2차 확장
- 자기개선 품질 루프(`constant`/`drop`/`silent` 등 지표 감시) — 데이터가 쌓인 뒤 2차
- R&R(임원 역할) 대조 상당 기능 — 이 도메인에 대응 개념 없음
- MCP 서버 마운트 — 필요해지면 추가
- 다국어 출력 — 한국어만

## 아키텍처

```
사용자 입력 (채팅 질의응답 + 문서 업로드: PDF/PPT/CSV)   [1차]
CRM/GA4 등 API 연동                                      [2차, 확장]
        │
        ▼
backend (FastAPI) ──────── frontend (Next.js)
  ① 입력 수집 → ② 정규화(구조화: 채널/캠페인/기간/지표)
  → ③ 병렬 진단 D1~D3 ∥ V·V2 (교차검증)
  → ④ 타임라인 연속성 (T1) → 총평
  → ⑤ Action Items 생성 → 종합 리포트(md/docx) + 이력(DB)
        │
        ▼
LLM 백엔드 (hermes-gateway 경유 — 기존 사내 인프라 재사용)
```

컨테이너 구성은 하네스와 동일하게 3개(db/backend/frontend), `docker compose up`
두 줄 기동을 유지한다. DB는 SQLite로 시작하고(단일 사용자·1차 범위 데이터량
기준 충분), 다중 사용자·동시 실행이 필요해지면 Postgres로 전환한다.

## 에이전트 카탈로그

`AGENT_CATALOG`처럼 `needs`(실행 그래프의 엣지)를 명시적으로 선언하고, 실행이
그 선언을 지키는지 테스트로 검사하는 패턴을 그대로 가져온다 — 하네스에서
암묵적 그래프가 두 번 조용히 어긋난 전례가 있다(화면이 실행 단계를 잘못
표시, 읽지도 않는 산출을 기다리며 대기).

| ID | 관점 | 출력 | needs |
|---|---|---|---|
| D1 현황진단관 | 채널·캠페인별 성과/강약점 | 진단 매트릭스(원문 인용) | () |
| D2 기회·리스크 정리관 | 사업 임팩트 순 | Top5 기회 / Top5 리스크 | () |
| D3 Critical Point 도출관 | 임팩트×시급성 | 방치 시 치명적인 포인트 + 필요 결정 | () |
| V 진단 교차검증관 | 환각·과탐 방지 | D1을 안 보고 원문만으로 독립 재탐지 → 확정/확인필요 | () |
| V2 기회·리스크 교차검증관 | D2 누락 점검 | 원문만 독립 도출 → D2에 없는 항목만 "추가 지적" | () |
| T1 타임라인 정합관 | 회차를 넘는 연속성 | 이번 진단 이슈 ↔ 과거 진단 동일성 판정(+반박 검증) | (D1,V,D2,D3) |
| Action Items 생성관 | 실행 전환 | 담당·기한·우선순위가 붙은 실행 항목 | (D1,D2,D3,T1) |
| V3 총평 사실검증관 | 총평 환각 방지 | 문장별 근거 대조 → 미근거 주장 지적, 1회 재작성 | (D1,D2,D3,V,V2,T1) |

D1~D3·V·V2는 서로 결과를 받지 않으므로 병렬 실행한다(독립 재도출이어야
교차검증이 성립하는 것은 하네스가 실측으로 확립한 원칙 — Top-N 선정처럼
"판단"의 성격을 가진 산출은 재도출로 검증할 수 없고, 대신 "다른 목록이
추가로 지적한 항목"으로 누락 점검에만 쓴다).

## 정확도 규율

1. **독립 재도출**: V·V2는 D1/D2 결과를 모른 채 원문만으로 재도출한다. 양쪽이
   찾은 것만 `확정`, 한쪽만 찾은 것은 `확인 필요`로 표기하고 항목을 버리지
   않는다.
2. **축자 근거 그라운딩**: 서술(종합)과 인용(원문)을 별개 필드로 받는다.
   판정은 인용 단위로 한다 — 진짜 인용에 가짜 인용이 섞이면 가짜만 빼고
   항목은 남긴다. 서술 필드 자체는 그라운딩하지 않는다(하네스가 실측으로
   확인: 서술을 검사하면 여러 자료를 종합한 정상 항목이 전멸한다).
3. **총평 사실검증**: V3가 총평 입력에 축자 근거를 함께 받아 문장별로 대조,
   미근거 주장을 지적하면 1회 재작성한다. 그래도 남으면 숨기지 않고 경고로
   낸다.
4. **반박 검증**: T1이 이은 타임라인 항목은 "실은 다른 사안"이라는 반박을
   통과해야 유지된다. 단순 유사도(Jaccard 등)는 후보를 넓게 걷어내는 recall
   필터로만 쓰고, 동일 사안 여부의 최종 판정은 LLM에 맡긴다 — 하네스가
   실측한 임계값의 오탐/정탐 여유가 0.02로 사실상 없었다.
5. **판단 보류 표기**: 입력 데이터가 없어 판단할 수 없는 경우 "없음"이 아니라
   "판단근거없음"으로 구분 표기한다. 데이터 부재와 실제 부재는 다른 사실이다.
6. **시스템이 판정을 조용히 고르지 않는다**: 두 에이전트의 판정이 갈리면
   둘 다 나란히 싣는다. 어느 쪽이 맞는지는 사용자가 정할 일이다.

## 입력 / 데이터 모델

- 1차: 사용자가 채팅으로 질문에 답하거나 문서(PDF/PPT/CSV)를 업로드하면
  정규화 에이전트가 채널/캠페인/기간/핵심 지표로 구조화한다.
- 진단은 "회차" 단위로 저장한다(하네스의 週에 대응). 회차 주기는 고정하지
  않고 사용자가 지정(주간/월간/캠페인 단위 등) — 타임라인 연속성 판정의
  기준 단위가 된다.
- 2차 확장(CRM/GA4 API 연동)도 같은 정규화 스키마로 흘러들어오도록 설계해
  둔다(정규화 계층에서 소스를 흡수, 에이전트 계층은 소스를 모른다).

## 산출물

현황진단(D1~D3 통합) + 타임라인(T1, "N회차째 반복" 표기) + Action Items
(담당·기한·우선순위) 리포트를 md/docx로 생성하고 이력 DB에 저장한다. 리포트는
입력 커버리지를 분모와 함께 쓴다(예: "5/6개 채널 데이터 확보") — 데이터가
없는 채널의 "이슈 없음"은 확인된 것이 아니다.

## 기술 스택

- Backend: FastAPI (하네스와 동일 — 팀에 이미 익숙한 스택)
- Frontend: Next.js
- DB: SQLite (1차) → Postgres (2차, 필요 시)
- LLM: hermes-gateway 경유 (사내 기존 인프라 재사용, 클라이언트 키 관리·rate
  limit·다중 인스턴스 라우팅을 게이트웨이가 맡는 이점을 그대로 가져온다)
- 오케스트레이션: 프레임워크(LangGraph 등) 없이 `asyncio` 직접 구현 — 하네스가
  같은 이유로 기각했다: 에이전트별 엔진 선택, 계측(`_tracked`) 같은 이 제품
  고유의 요구가 프레임워크의 노드 추상 밖에 있고, 지금 그래프는 분기 없는
  DAG라 선언 문법의 가치가 작다. 조건부 라우팅이나 재시도 루프가 생기면
  재검토한다.
